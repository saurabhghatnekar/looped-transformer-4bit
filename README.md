# Replicating Inkling 2 Mini: a looped transformer pretrained with 4-bit forward passes

Goal: replicate Thinking Machines' [Inkling 2 Mini](https://thinkingmachines.ai/news/inkling-2-mini/)
end to end, starting with pretraining in 4-bit (NVFP4) on Blackwell GPUs.

## Done / Not done

### Done
- **Architecture & 4-bit recipe ([loopfp4/inkling.py](loopfp4/inkling.py), [loopfp4/nvfp4.py](loopfp4/nvfp4.py)):** Text decoder and 4-bit training recipe implemented and verified against Hugging Face `inkling2_loop` (`4e-7` at 1, 2, 3, and 5 passes), plus 9 core and 19 Inkling unit tests (`tests/test_core.py`, `tests/test_inkling.py`).
- **Live Hugging Face data pipeline ([prepare_data.py](prepare_data.py)):** Streamed and verified `HuggingFaceFW/fineweb-edu:sample-100BT` with `thinkingmachines/Inkling-2-Mini` (`200,058` vocab, `uint32` shards).
- **Verified all three expert backends on real NVIDIA B200 (`191.51 GB`) GPUs:** Tested `sim`, `te`, and `grouped` end-to-end on Modal (`modal_verify_b200.py`, `modal_verify_ddp_and_perf.py`, `modal_verify_part2.py`).
- **Optimized `5b` single-GPU B200 throughput `16.4x`:** Pushed `5b` (`5.403 B` stored, `48` layer apps/token, FP32 master weights + AdamW) from `1,412 tok/s/B200` (**\$78,691** / 100B tokens @ \$4/GPU-hr, `145.52 GB`) to **`21,719 tok/s/B200`** with exact Four-Over-Six NVFP4 (**\$5,116**, `136.85 GB`) and **`23,175 tok/s/B200`** in BF16 (**\$4,794**, `136.85 GB`) via zero-sync unpadded `torch._grouped_mm`, custom zero-atomic Triton Flash-RPB+Sink attention ([loopfp4/triton_attn.py](loopfp4/triton_attn.py), `<= 5e-7` IEEE FP32 parity), contiguous causal convs, fused attention residuals, compiled `chunk=4096` cross-entropy, hoisted loop message states, `layer.compile()`, and selective activation checkpointing (`--grad-checkpoint-mode sac`).
- **Multi-GPU `2x NVIDIA B200` NCCL DDP + `--resume`:** Verified on both `smoke` and `5b` (`41,420–41,510 tok/s` combined at `bs=24`, `97.4%` scaling efficiency, `idle_experts=0`, clean resume from saved checkpoints).
- **Prune, heal, export & writeup:** Verified prune-and-heal (`prune_experts.py`), lossless 4-bit export (`export_nvfp4.py`), and documented all B200 measurements in [docs/blog-b200-cost-optimization.md](docs/blog-b200-cost-optimization.md).

### Not done
- **Full 100B+ token pretraining run:** Throughput, convergence on small data, `2x B200` DDP, and checkpoint resume are verified; a long pretraining run has not been launched yet.
- **Hardware SM100 NVFP4/MXFP8 grouped GEMMs for `E >= 128` experts:** TE `2.20.2` grouped quantizers hard-fail at `num_tensors <= 64`, `torchao`'s `fused_pad_token_groups` fails at `num_groups <= 32`, and PyTorch `2.15` `F.scaled_grouped_mm` lacks NVFP4 `BlockWise1x16` kernels (`ValueError: No gemm implementation was found`). Today `--backend grouped` runs exact Four-Over-Six NVFP4 straight-through quantization over BF16 `torch._grouped_mm`.
- **Closing the final `1.3x–1.5x` from \$4.8k–\$5.1k into \$2k–\$4k (`30k+ tok/s/B200`):** Requires SM100 hardware grouped FP4/FP8 supporting `E >= 128` plus a Warp-Specialized/TMA FlashAttention-4 RPB+Sink kernel.
- **Expert Parallelism / FSDP2 sharding:** `train.py` replicates the full model per GPU, so `5b-pretrain` (`241 GB`), `mini` (`26.1 B`), and `mini-pretrain` (`75.0 B`) cannot fit on a single B200 yet.
- **Model & pipeline extras:** No stochastic rounding in TE's MXFP8 backward (`tml` rounds to nearest), no vision tower, no multi-token-prediction head, no KV cache for generation, no SFT/RL stages, no evaluation harness, and no loader for the released Inkling 2 Mini Hugging Face checkpoint weights.

## What matches the published model

Sources: the release post, the [4-bit training article](https://thinkingmachines.ai/blog/end-to-end-4-bit-training/),
the released `config.json`, and the reference code in Hugging Face transformers
(`models/inkling2_loop`, `models/inkling2`).

**Architecture** (`loopfp4/inkling.py`). `tests/test_reference.py` builds a small random
reference model, copies its weights in, and compares logits: they agree to 4e-7 at 1, 2, 3
and 5 passes.

- 24 layers in four blocks of six; layers 6 to 17 run three times with shared weights (48 layer applications per token).
- Attention residuals: each layer reads a learned mix of earlier block outputs instead of one running sum.
- Loop messages: later passes read the previous pass's block outputs through low-rank gates that start closed.
- Sliding-window attention (1,024 tokens) with a global-attention layer every sixth layer; grouped queries (24 heads, 8 key/value heads).
- Content-dependent relative position bias, attention sinks, gated attention output, short causal convolutions.
- Mixture of experts: sigmoid router, top 8, softcapped SwiGLU, 128 experts (384 before pruning).
- `plan.py --preset mini` gives 26.07B stored and 3.14B active parameters. The model card says 26.4B and 3.4B including a ~0.3B vision tower.

**4-bit recipe** (`loopfp4/nvfp4.py`), as described in the article:

| Published | Here |
|---|---|
| NVFP4 forward passes in the expert layers; attention and the rest in higher precision | same |
| Last 4 layers' experts in MXFP8 | same |
| One outer scale per expert for weights, per token for activations; 1x16 block scales | same |
| Four-Over-Six scale selection on activations | same |
| Backward GEMMs in MXFP8 on the quantized forward operands, re-quantized after the transpose with stochastic rounding | same |
| FP32 master weights, quantized on every forward pass | same |
| Dedicated fused kernel on GB300, 15 PFLOPS in NVFP4 | their kernel is not public. `--backend grouped` (fastest on B200, up to `23,175 tok/s/B200`) runs zero-sync `torch._grouped_mm` BF16 with optional Four-Over-Six NVFP4 STE quantization; `--backend te` uses TE `GroupedLinear` (verified on B200, hits TE `CustomRecipe` loop / `<= 64` limits); `--backend sim` simulates 4-bit numerics in ordinary float arithmetic anywhere |
| Tokens sent between GPUs in NVFP4, Hadamard transform + S2F6 for gradients | not implemented (no cross-GPU expert dispatch here) |

## Three ways to run the expert layers

- **`--backend sim` (default):** rounds every operand to its 4-bit value and multiplies in ordinary float arithmetic. Runs on CPU, MPS, or CUDA and reproduces 4-bit training numerics with no speedup.
- **`--backend grouped` (recommended on B200):** keeps the same stacked weights and checkpoints as `sim`, sorts token-expert pairs without host syncs, quantizes activations once per token before `top_k` replication (with `--quant nvfp4`), and runs unpadded `torch._grouped_mm` BF16 kernels. Combined with Triton Flash-RPB+Sink attention, `--compile`, and `--grad-checkpoint-mode sac`, this achieves **`21,719 tok/s/B200`** (`--quant nvfp4`) and **`23,175 tok/s/B200`** (`--quant none`, BF16).
- **`--backend te` (Blackwell + Transformer Engine):** hands expert GEMMs to TE's `GroupedLinear` with `--te-align 32`. Verified on real B200s (`3,756 tok/s/B200`), though TE `2.20.2` falls back to a per-expert Python loop on `CustomRecipe` (`tml`/`rowscaled`) and hits `num_tensors <= 64` limits on `E >= 128` grouped quantizers.

`--te-recipe` picks the quantization options for `--backend te`:

| | `tml` (default) | `rowscaled` | `nvidia` |
|---|---|---|---|
| Forward GEMM | NVFP4 | NVFP4 | NVFP4 |
| Weight block scales | 1x16, as published | 1x16 | 16x16 tiles |
| Activation outer scale | per token, as published | per token | per tensor |
| Four-Over-Six on activations | yes, as published | no | no |
| Backward GEMMs | MXFP8, as published | MXFP8 | NVFP4 with stochastic rounding |
| Backward operands | re-quantized from the dequantized 4-bit forward values, as published | same | quantized from the originals |
| Hadamard transform | off | off | on |
| Built from | Transformer Engine's fine-grained recipes (experimental) | a factory Transformer Engine ships, unmodified | its default NVFP4 recipe |

- **`tml` is the published recipe except for one detail.** Thinking Machines re-quantizes the
  backward operands with stochastic rounding; Transformer Engine's MXFP8 quantizer has no
  stochastic-rounding option, so that step rounds to nearest.
- **`rowscaled`** is Transformer Engine's own `nvfp4_row_scaled_fwd_mxfp8_bwd_factory`. `tml`
  is that factory plus Four-Over-Six.
- **`nvidia`** is NVIDIA's published pretraining recipe and uses only stable options (verified on B200: crashes on `E >= 128` when native grouped path triggers `num_tensors <= 64`).
- **Checkpoints are identical across `sim`, `te`, and `grouped`**, so a model can be trained on B200 and pruned, exported, or sampled anywhere.

## What is not published, and what I chose instead

These choices are mine. Treat them as starting points to tune, not as the recipe.

- **Initialisation.** Normal(0, 0.02) for matrices, zeros for attention-residual queries (as in the reference), and zero gate projections so loops start closed (the post says they do).
- **Expert load balancing.** A per-expert selection bias nudged towards even load each step. The released checkpoint carries such a bias, but how it was trained is not stated.
- **Optimizer, learning rate, batch size, pretraining token count, when pruning happened.** AdamW with cosine decay here.
- **Multi-token-prediction head and vision tower.** Both are in the released weights; neither is built here.

## Laptop check

```bash
python tests/test_core.py
python tests/test_inkling.py
python prepare_data.py --source data/raw/tinystories-valid.txt --tokenizer bytes --out data/tinystories-bytes
python train.py --preset smoke --data data/tinystories-bytes --out runs/ink-fp4 --batch-size 16 --steps 300
python prune_experts.py runs/ink-fp4/ckpt.pt runs/ink-fp4/pruned.pt --keep 16
python train.py --init runs/ink-fp4/pruned.pt --data data/tinystories-bytes --out runs/ink-fp4-healed --steps 100
python export_nvfp4.py runs/ink-fp4-healed/ckpt.pt runs/ink-fp4-healed/model-nvfp4.pt
```

`tests/test_reference.py` needs a transformers release that includes `inkling2_loop` (5.24 or
later); the other tests need only PyTorch.

### What the laptop check showed

The `smoke` preset (Inkling's layout at 10.6M parameters: 12 layers, 4 of 32 experts, layers
3 to 8 looped three times) on an M2 Max, TinyStories bytes, 4,096 bytes per step, same seed.
Validation loss in nats per byte, 20 batches per evaluation, one run each:

| Run | step 100 | step 200 | step 300 |
|---|---|---|---|
| full precision | 1.927 | 1.348 | **1.196** |
| 4-bit forward, MXFP8 backward | 1.932 | 1.354 | **1.214** |

- **The 4-bit recipe trains.** It ends 0.018 nats (1.5%) behind full precision and tracks it throughout.
- **The loop is used.** The message gates opened from zero, and running the trained 4-bit
  model with one pass instead of three raises its loss from 1.214 to 1.323. This is not a
  comparison against a model trained without looping; that run was not done for this model.
- **Load balancing works.** No expert was left idle by step 200, and the busiest expert's
  load fell from 3.3x an even share at its peak to 2.0x. (Idle counts in the first 100 steps
  of the log are inflated, because the running average they come from starts at zero.)
- **Prune and heal works mechanically.** Cutting 32 experts to the 16 most used raised the
  loss from 1.214 to 1.700; 100 more steps brought it to 1.151. The kept experts had been
  handling only 54% of the tokens, so this was a harsher cut than a well-trained router
  would face.
- **Export works.** The NVFP4 experts pack to 4-bit codes that reproduce the training weights exactly.
- **Speed.** About 1,760 bytes per second in 4-bit and 2,360 in full precision on the Apple
  GPU: the simulated 4-bit path costs 25% here.

This check says the code is correct and the recipe converges on a toy problem. It says
nothing about quality or speed at real scale.

## Sizes

```bash
python plan.py --preset mini-pretrain
python plan.py --preset 5b
```

| Preset | What it is | Stored | Active per token | Training state (weights, grads, Adam) | 4-bit checkpoint |
|---|---|---|---|---|---|
| `mini-pretrain` | Inkling 2 Mini as pretrained, 384 experts | 75.0B | 3.15B | 1,200 GB | 50 GB |
| `mini` | Inkling 2 Mini as released, 128 experts | 26.1B | 3.14B | 417 GB | 18.9 GB |
| `5b-pretrain` | same layout at width 1,024, 384 experts | 15.1B | 0.88B | 241 GB | 10.4 GB |
| `5b` | same layout at width 1,024, 128 experts | 5.4B | 0.87B | 86 GB | 4.2 GB |
| `smoke` | 12 layers, width 128, byte vocabulary | 10.6M | – | – | – |

- **Only `5b` fits today.** `train.py` keeps a full copy of the model on every GPU. The other
  three exceed one B200's memory and need the experts sharded across GPUs, which is not written.
- **`5b` is a small model in use.** Most of its 5.4B parameters are experts a token does not
  touch; per token it computes like a 0.9B model, of which 0.4B is the 200k-word embedding
  and output tables.
- **Measured compute for `5b` on B200** (`plan.py --tok-per-s-per-gpu`): **`1,199–1,279` GPU-hours** (**\$4,794** in BF16 at `23,175 tok/s/B200`, or **\$5,116** with exact Four-Over-Six NVFP4 at `21,719 tok/s/B200` per 100B tokens at \$4 per GPU-hour).

## Running on Blackwell

1. **Data (verified with FineWeb-Edu + Inkling-2-Mini tokenizer):**
   ```bash
   python prepare_data.py --source hf:HuggingFaceFW/fineweb-edu:sample-100BT \
       --tokenizer hf:thinkingmachines/Inkling-2-Mini --out /data/fineweb-edu-inkling --max-tokens 100e9
   ```
2. **Train `5b` on 8x B200 with the verified fast path:**
   ```bash
   torchrun --nproc_per_node=8 train.py --preset 5b --data /data/fineweb-edu-inkling --out runs/5b \
       --backend grouped --quant nvfp4 --grad-checkpoint --grad-checkpoint-mode sac --compile \
       --batch-size 32 --grad-accum 1 --steps 190735 --lr 2e-4 --warmup 3000
   ```
   Read `tok_per_s` from `log.jsonl` and pass `--tok-per-s-per-gpu` to `plan.py` for cluster cost estimates.
3. **Run the Modal verification suites:** `modal run modal_verify_part2.py` (re-verifies Triton attention parity, `grouped` edge cases, single-GPU `5b` throughput, and `2x B200` NCCL DDP + `--resume`).
4. **Pretrain, prune, heal** using `prune_experts.py`, `train.py --init ...`, and `export_nvfp4.py`.

## Earlier dense model

Before the reference code was read, `loopfp4/model.py` approximated the design with dense
layers and scalar loop gates. Its laptop results (5.4M parameters, 1,000 steps, validation
loss in nats per byte) still stand for that model: full precision 0.790, 4-bit 0.805, and
4-bit without looping 0.810. It is kept under the `dense-*` presets.
